# mdreader

A lightweight, fast-launching desktop Markdown viewer. Double-click a `.md`
file (or right-click → Open With) on Windows, macOS, or Linux and it opens
in mdreader — no editor, no project to load, just the rendered document.

- Full CommonMark + GitHub-flavored Markdown (tables, task lists,
  strikethrough, footnotes)
- Syntax-highlighted code fences
- Mermaid diagrams and KaTeX math, loaded only for documents that use them
- Tabs, a table-of-contents sidebar, and in-page find (⌘/Ctrl-F)
- Light / Dark theme
- Registers as a `.md`/`.markdown`/`.mdown`/`.mkd` handler on all three OSes

## Why it's fast

Markdown is parsed and rendered to HTML in **Rust**, not JavaScript — the
frontend is a single static HTML/CSS/JS bundle with no framework and no
bundler, so there's nothing to hydrate. Mermaid (~3.5 MB) and KaTeX
(~270 KB) are fetched from disk only when a document actually contains a
diagram or math; a plain document never touches either. Cold start is a
few hundred milliseconds.

## Architecture

```
mdreader/
├─ src-tauri/            Rust backend (Tauri v2 shell)
│  ├─ src/
│  │  ├─ lib.rs           App entry point: the three file-open paths,
│  │  │                   Tauri commands, plugin registration
│  │  ├─ render.rs        Markdown → sanitized HTML (the core pipeline)
│  │  └─ main.rs          Stock 3-line Tauri bin entry point
│  ├─ build.rs            Generates src/code-theme-{light,dark}.css from
│  │                      syntect's bundled themes at compile time
│  ├─ tauri.conf.json     Window config + bundle.fileAssociations (the
│  │                      config that makes OS file-association work)
│  └─ capabilities/       Tauri's permission manifest for the webview
└─ src/                   Static frontend — no build step
   ├─ index.html           Page shell: tab bar, sidebar, find bar
   ├─ styles.css           All app styling, incl. light/dark tokens
   ├─ app.js               Tabs, TOC, find, theme, lazy-loading — all UI logic
   ├─ code-theme-*.css      Generated by build.rs, do not edit by hand
   └─ vendor/               Mermaid and KaTeX, vendored locally (no CDN)
```

### Rendering pipeline (`render.rs`)

One pass over the [`pulldown-cmark`](https://docs.rs/pulldown-cmark)
event stream:

1. **Parse** the source as GFM (tables, strikethrough, task lists,
   footnotes, heading attributes).
2. **Transform** headings and code fences into `Event::Html(..)` inline in
   the stream — headings get slugged IDs and a hover anchor link; code
   fences get [`syntect`](https://docs.rs/syntect)-highlighted spans (or,
   for a ` ```mermaid ` fence, are left as raw text for mermaid.js to pick
   up client-side). Everything else — tables, footnotes, inline markup —
   passes through untouched.
3. **Resolve** relative image/link destinations to absolute filesystem
   paths (`Path::join` + percent-decode + best-effort normalize), since
   Rust is the only side that knows the document's directory. External
   URLs, `mailto:`/`tel:` links, and `#anchor`s are left alone.
4. Render the whole transformed stream through **one**
   `pulldown_cmark::html::push_html` call. This matters: `HtmlWriter`
   carries state across events (table head/body, footnote numbering), so
   calling it more than once per document — e.g. once per event — silently
   produces wrong output for tables and footnotes.
5. **Sanitize** the result with [`ammonia`](https://docs.rs/ammonia), a
   whitelist HTML sanitizer.

The frontend never runs a Markdown parser — it receives finished, sanitized
HTML, a heading list (for the TOC), and two booleans (`has_mermaid`,
`has_math`) that gate the lazy-loaders.

### The three ways a file can open (`lib.rs`)

An OS can hand mdreader a file to open in three different shapes, and all
three funnel into one `queue()` function:

1. **Cold start, Windows/Linux** — the path is a plain `argv` entry, read
   in `.setup()`.
2. **Cold start, macOS** — the path never appears in `argv`; it arrives as
   `RunEvent::Opened`, which (like `.setup()`) always runs *after* the
   window is built but before the frontend has loaded and attached its
   listener.
3. **App already running** — `tauri-plugin-single-instance` forwards the
   new process's `argv` into the running instance.

Because the window exists before the page does, `queue()` always pushes to
a `pending` queue first and only *optionally* emits an event as a hint —
never the payload itself. The frontend drains the queue on load and again
on every `files-pending` event, so a file is never silently lost to
startup-ordering.

### Frontend (`src/app.js`)

No framework, no bundler — `index.html` + `styles.css` + `app.js` is the
whole UI. Each open tab gets its own persistent `<article>` element
(created once, kept alive, toggled via a CSS class) rather than
re-rendering a shared node on every switch — so switching tabs is free and
Mermaid/KaTeX only ever render once per document, the first time its tab
is actually shown (both need real layout to measure text, so they can't
run against a `display: none` element).

## Prerequisites

- [Rust](https://rustup.rs/) (stable toolchain)
- [Node.js](https://nodejs.org/) — only used to run the Tauri CLI, no
  frontend build tooling
- Platform build tools: Xcode Command Line Tools (macOS), the Visual
  Studio Build Tools + WebView2 (Windows), or `webkit2gtk`/`libayatana-appindicator`
  (Linux) — see [Tauri's prerequisites guide](https://v2.tauri.app/start/prerequisites/)

## Build & run

```bash
npm install
npm run tauri dev              # launch with hot-reload
npm run tauri dev -- some.md   # launch with a file already open
```

Run the Rust test suite (markdown rendering, sanitization, path
resolution):

```bash
cd src-tauri && cargo test
```

## Package / install

```bash
npm run tauri build
```

Each platform's installer has to be built *on* that platform — Tauri
doesn't cross-compile installers. `.github/workflows/build.yml` does this
in CI: on every push/PR (or manually via "Run workflow"), it builds all
three in parallel and uploads each as a downloadable Actions artifact —
no GitHub Release is created, it's build-only.

Produces a native installer under `src-tauri/target/release/bundle/`:

- **Windows** — an NSIS `.exe` installer. Registers `.md` etc. in
  `HKCU\Software\Classes` so mdreader appears in "Open with"; a portable
  `.exe` alone cannot register file associations. Windows does not allow
  installers to silently become the *default* handler — that's a one-time
  user click after install.
- **macOS** — a `.app` bundle (and `.dmg`). Move it to `/Applications` and
  launch it once to register with Launch Services; Finder's "Open With"
  will then list it. Unsigned builds need a right-click → Open on first
  launch to pass Gatekeeper.
- **Linux** — `.deb` and `.rpm`, each shipping a `.desktop` file with
  `MimeType=text/markdown`. Install via the system package manager so
  `update-desktop-database` runs and the file manager picks it up.

The extension list, MIME type, and per-OS metadata all come from one
place: `bundle.fileAssociations` in `src-tauri/tauri.conf.json`.

## Tech stack

| | |
|---|---|
| App shell | [Tauri v2](https://v2.tauri.app/) (Rust + the OS's native webview — WebView2/WKWebView/WebKitGTK) |
| Backend language | Rust |
| Markdown parsing | [pulldown-cmark](https://docs.rs/pulldown-cmark) |
| Syntax highlighting | [syntect](https://docs.rs/syntect) |
| Sanitization | [ammonia](https://docs.rs/ammonia) |
| Frontend | Vanilla HTML/CSS/JavaScript — no framework, no bundler |
| Diagrams | [Mermaid](https://mermaid.js.org/) (vendored, lazy-loaded) |
| Math | [KaTeX](https://katex.org/) (vendored, lazy-loaded) |
| Tooling | Node.js + npm (Tauri CLI only) |
